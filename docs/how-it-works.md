# Как это работает: VLESS + XHTTP + Reality

Этот документ объясняет техническую схему, которую использует форк по умолчанию. Он предназначен для тех, кто хочет понять, что происходит «под капотом», и почему выбраны именно эти настройки.

## 🖼️ Схема рукопожатия

```text
┌─────────────┐           ┌──────────────────────────────────────┐           ┌─────────────┐
│   Клиент    │           │           Сервер (VPS)               │           │   Интернет  │
| v2rayN и т.д)│          │                                      │           │             │
└──────┬──────┘           └──────────────────┬───────────────────┘           └──────┬──────┘
       │                                     │                                      │
       │ 1. TLS ClientHello (SNI: karkkainen.com)                                   │
       │ ───────────────────────────────────>│                                      │
       │                                     │ 2. Reality проверяет SNI             │
       │                                     │    и отдаёт сертификат               │
       │ 3. TLS ServerHello                  │    (валидный для karkkainen.com)     │
       │ <───────────────────────────────────│                                      │
       │                                     │                                      │
       │ 4. VLESS-запрос (UUID + XHTTP)      │                                      │
       │   ⚠️ Flow: только с VLESS Encryption│                                      │
       │ ───────────────────────────────────>│                                      │
       │                                     │ 5. Xray проверяет UUID,              │
       │                                     │    распаковывает XHTTP               │
       │                                     │                                      │
       │                                     │ 6. Запрос к целевому сайту           │
       │                                     │ ────────────────────────────────────>│
       │                                     │                                      │
       │                                     │ 7. Ответ от сайта                    │
       │                                     │ <────────────────────────────────────│
       │                                     │                                      │
       │ 8. Ответ клиенту (через XHTTP)      │                                      │
       │ <───────────────────────────────────│                                      │
       │                                     │                                      │
```

## 🔍Что происходит на каждом этапе

 TLS ClientHello (SNI: finnish.com) — Клиент начинает соединение, «представляясь» как браузер, который хочет открыть finnish.com. В поле SNI передаётся имя этого домена.

Reality проверяет SNI — Сервер (Xray) видит SNI. Если он совпадает с настроенным Dest (например, finnish.com:443), Reality отдаёт валидный TLS-сертификат для этого домена. Для DPI это выглядит как обычное подключение к finnish.com. 

TLS ServerHello — Клиент получает сертификат и завершает рукопожатие. Соединение установлено. DPI не видит ничего подозрительного — это просто HTTPS к финскому сайту.

VLESS-запрос (UUID + XHTTP) — Внутри установленного TLS-туннеля клиент отправляет VLESS-запрос. Он содержит UUID (идентификатор пользователя) и данные, упакованные в XHTTP (транспорт, который маскирует трафик под HTTP/2 или HTTP/3 запросы).

Xray проверяет UUID и распаковывает XHTTP — Сервер (Xray) проверяет UUID. Если он верный — распаковывает XHTTP и понимает, куда клиент хочет подключиться (например, www.google.com:443).

Запрос к целевому сайту — Xray отправляет запрос от имени клиента (через freedom outbound) к реальному сайту (Google).

Ответ от сайта — Сайт отвечает Xray.

Ответ клиенту (через XHTTP) — Xray упаковывает ответ обратно в XHTTP и отправляет клиенту через тот же TLS-туннель.

## 🎯 Почему SNI должен соответствовать серверу

Reality маскирует соединение под обычный HTTPS-визит к сайту, указанному в SNI. Если сайт и сервер находятся в одной инфраструктуре (страна, CDN, ASN) — это выглядит естественно. Если нет — DPI видит аномалию.

```text
🟢 ПРАВИЛЬНО: SNI и сервер в одном регионе
┌─────────────┐      TLS ClientHello       ┌─────────────────────┐
│  Клиент     │ ──── (SNI: finnish.com) ──>│  Сервер в Финляндии │
│  в РФ       │                            │  IP: 95.x.x.x       │
└─────────────┘                            └─────────────────────┘
                                                    │
                                           DPI видит: «Финский IP + 
                                           финский домен = норма»

🔴 НЕПРАВИЛЬНО: SNI в США, сервер в Финляндии
┌─────────────┐      TLS ClientHello       ┌─────────────────────┐
│  Клиент     │ ──── (SNI: usa-site.com) ─>│  Сервер в Финляндии │
│  в РФ       │                            │  IP: 95.x.x.x       │
└─────────────┘                            └─────────────────────┘
                                                    │
                                           DPI видит: «Американский 
                                           домен на финском IP = 
                                           подозрительн
```
Вывод: выбирайте SNI, который логически связан с локацией сервера (страна, CDN, ASN). Это снижает риск детекта и блокировки.
