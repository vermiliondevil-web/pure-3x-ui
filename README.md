> **О бейджах.** Бейдж `Build and Release` показывает **последний прогон** workflow. Если он **красный** — это **не значит**, что ваш форк сломан. Возможные причины:
>
> - **Upstream-автор** (MHSanaei) запушил коммит, который **не прошёл** сборку (`npm run build` или `go build`).
> - **`Sync Upstream`** подтянул этот коммит в ваш `main`.
> - **`Build and Release`** попытался собрать — и **упал** (потому что код **сам по себе сломан** у автора).
> - **Ваш форк** при этом **не сломан** — просто upstream **временно нестабилен**.
>
> **Что делать:**
>
> - **Ничего.** Подождите, пока MHSanaei **исправит** свой код.
> - Или **откатите** проблемный коммит (`git reset --hard HEAD~1 && git push --force`).
> - **Релиз** `v3.9.2` (последний стабильный) **продолжает работать** — вы можете **не обновляться** до исправления.
>
> То же касается бейджа `Sync Upstream` — если он **красный**, значит, merge **не прошёл** (конфликты). Это **тоже не критично** — можно **разрешить конфликты вручную**.

## Установка

### Основной способ (рекомендуется)

Запустите от имени **root**:

```bash
bash <(curl -Ls https://cdn.jsdelivr.net/gh/vermiliondevil-web/pure-3x-ui@main/install.sh)
```

Этот способ **работает из России** — скрипт скачивается через CDN jsDelivr, который не блокируется РКН.

### Альтернативные способы

Если основной способ не работает — попробуйте один из этих:

```bash
# 1. Через github.com/raw (редиректит на raw.githubusercontent — нужен VPN)
bash <(curl -Ls "https://github.com/vermiliondevil-web/pure-3x-ui/raw/main/install.sh")

# 2. Через jsDelivr с конкретным коммитом (обход кэша CDN — всегда свежая версия)
bash <(curl -Ls https://cdn.jsdelivr.net/gh/vermiliondevil-web/pure-3x-ui@1ac852e1/install.sh)

# 3. Через jsDelivr с тегом (стабильный релиз)
bash <(curl -Ls https://cdn.jsdelivr.net/gh/vermiliondevil-web/pure-3x-ui@v3.9.2/install.sh)
```

**Особенности способов:**

| № | Способ | Особенность |
|---|---|---|
| **1** | `github.com/raw` | Редирект на `raw.githubusercontent.com` → нужен VPN/прокси |
| **2** | `jsDelivr @<коммит>` | Ссылка на конкретный коммит → **не кэшируется**, всегда свежая |
| **3** | `jsDelivr @<тег>` | Ссылка на стабильный релиз → кэшируется 12ч, но тег неизменен |

### Что делает скрипт

1. Определяет ОС и архитектуру.
2. Устанавливает зависимости.
3. Скачивает последний релиз из **этого** репозитория.
4. Проверяет `.sha256`.
5. Настраивает сервис, базу данных, SSL.
6. Выводит **логин, пароль, порт, webBasePath** и **URL** панели.

## Обновление

### Через UI (кнопка «Обновить»)

Панель **сама проверяет** последний релиз на GitHub через `api.github.com/repos/vermiliondevil-web/pure-3x-ui/releases/latest` и **скачивает** `update.sh` через jsDelivr.

**Как работает:**

1. Панель запрашивает последний тег.
2. Скачивает `update.sh` через jsDelivr.
3. `update.sh` вызывает `install.sh` (тоже через jsDelivr).
4. `install.sh` скачивает архив и обновляет панель.

**Важно:** кнопка «Обновить» **активна только если версия на GitHub выше** версии в файле `internal/config/version`.

### Через `install.sh`

```bash
bash <(curl -Ls https://cdn.jsdelivr.net/gh/vermiliondevil-web/pure-3x-ui@main/install.sh)
```

Скрипт подтянет последний релиз, сохранит базу и настройки.

### Xray core

Кнопка обновления Xray в панели **безопасна** — она тянет ядро напрямую с [XTLS/Xray-core](https://github.com/XTLS/Xray-core), где **нет** рекламы.

## ⚠️ Важно: российские VPS-провайдеры и блокировка VPN

Если вы используете **российский VPS-провайдер** (Timeweb, RocketCloud, Selectel, Beget, RUVDS и другие), **учтите**:

### Провайдеры обязаны блокировать VPN

Согласно поправкам **«Антифрод 3.0»** (Минцифры, 2026), российские хостинг-провайдеры **обязаны**:
- проверять клиентов по **реестру Роскомнадзора**;
- **отказывать** в обслуживании владельцам VPN/прокси;
- **прекращать** обслуживание по запросу силовых органов.

**На практике это означает:** даже если ваш VPS работает, провайдер может **фильтровать трафик** через **ТСПУ** (технические средства противодействия угрозам) на **своём уровне**.

### Что это значит для вас

**Симптомы «сволочного» провайдера:**
- `raw.githubusercontent.com` **не открывается** (TLS-хендшейк рвётся после `Server hello`).
- VPN-подключения **работают**, но **скорость** падает.
- Отдельные **сайты** (Meduza, BBC, DW) **не открываются** даже через VPN.
- `dig` возвращает **фейковые IP** для заблокированных доменов.

**Ваш RocketCloud** — **пример такого провайдера**:
- IP помечен как **VPN/Hosting** в публичных базах[citation:3].
- Отзывы: **поддержка не отвечает**, **производительность низкая**, **ребрендинг SkyHost с 90% негатива**[citation:14][citation:16].

### Что делать

**Вариант А: сменить провайдера** (рекомендую)

Ищите **зарубежного** хостера (Нидерланды, Германия, Финляндия) или **российского**, но с **минимальной цензурой**:

| Провайдер | Особенность |
|---|---|
| **AezaNet** | Anti-complaint VPS, данные в РФ и Европе, криптоплатежи, **без real-name**[citation:18] |
| **VDSina** | Серверы в NL, отзывы: **работает стабильно**, можно оплатить из РФ[citation:2] |
| **Doubleservers** | 88% одобрения, серверы в FR/DE/PL[citation:1] |
| **Soulful Hosting** | 82% одобрения, DE/PL[citation:1] |

**Вариант Б: остаться на российском, но использовать jsDelivr**

Ваш `install.sh` **уже** работает через **jsDelivr** — это **обход** блокировки `raw.githubusercontent.com`. **Это работает** — установка прошла успешно.

**Вариант В: обход на уровне сети**

- **IPv6** — часто **менее цензурирован**, чем IPv4[citation:5].
- **Свой DNS** через **DoH/DoT** (мы это делали).
- **VPN/прокси** для исходящих запросов.

### Почему это важно для этого проекта

`pure-3x-ui` **специально** использует **jsDelivr** вместо `raw.githubusercontent.com` — потому что **российские провайдеры** (как RocketCloud) **блокируют** `raw` на уровне **ТСПУ**.

**Если вы используете зарубежный VPS** — `raw` **работает** без обходов. **jsDelivr** всё равно **быстрее** и **надёжнее**.

**Если вы используете российский VPS** — `jsDelivr` **обязателен**. Без него `install.sh` **не работает**.

## Как это работает: синхронизация и релизы

В репозитории настроены **два GitHub Actions workflow**, которые работают **вместе**.

### `Sync Upstream` — раз в день (автоматически)

**Что это:** GitHub Actions **сам** запускает workflow **каждый день в 03:00 UTC** (06:00 МСК) — или **вручную** через вкладку Actions.

**Что он делает:**

1. Заходит в репозиторий Санаи (`MHSanaei/3x-ui`).
2. Проверяет, есть ли **новые коммиты** с прошлого раза.
3. Если есть — **подтягивает** их в ваш форк.
4. Запускает `scripts/remove-ads.sh` — **вырезает рекламу** и донаты.
5. Заменяет `raw.githubusercontent.com` на `cdn.jsdelivr.net` (обход РКН).
6. Брендирует `panel.go` и `update.sh`.
7. **Коммитит** изменения в ваш `main`.
8. **Пушит** на GitHub.

**Если новых коммитов нет** — пишет `Already up to date` и **завершается** (за 30 секунд).

**Что вы видите:**

- В Actions — **зелёный** прогон `Sync Upstream`.
- В `main` — **новый коммит** `chore: auto strip ads after upstream merge` (если upstream изменился).

**Что делать:** **ничего**. Всё работает автоматически.

### `Build and Release` — по тегу (по вашей команде)

**Что это:** GitHub Actions **запускается** только когда **вы создаёте тег** `v*` (например, `v3.9.3`).

**Что он делает:**

1. Вырезает рекламу (`scripts/remove-ads.sh`) — страховка.
2. Собирает фронтенд (`npm run build`).
3. Собирает Go-бинарник.
4. Скачивает Xray core с XTLS.
5. Упаковывает всё в `x-ui-linux-amd64.tar.gz` + `.sha256`.
6. **Публикует** релиз на GitHub.

**Если тег не создан** — **релиз не публикуется**.

**Что вы видите:**

- Новый тег `v3.9.3`.
- Через 10–15 минут — релиз `v3.9.3` с архивом в Assets.

**Что делать:** создать тег, когда хотите выпустить новый релиз.

### Сценарии работы

#### Сценарий 1: Санаи выпустил обновление

**Что происходит автоматически:**

1. **03:00 UTC** — `Sync Upstream` запускается.
2. Видит новые коммиты у Санаи.
3. Подтягивает их, вырезает рекламу, коммитит в ваш `main`.
4. Пушит на GitHub.
5. **Всё.** Релиз **НЕ создаётся**.

**Что вы видите:**

- Новый коммит в `main` — `chore: auto strip ads after upstream merge`.
- Обновлённые файлы (Go-код, фронтенд — **без рекламы**).
- **Всё ещё работает** панель **старого релиза** (`v3.9.2`).

#### Сценарий 2: Вы хотите выпустить новый релиз

**Что делаете вы:**

1. **Зайдите в SSH** на инженерный VPS:

   ```bash
   cd /root/pure-3x-ui
   git pull
   ```

2. **Поменяйте версию** на новую:

   ```bash
   echo -n "3.9.3" > internal/config/version
   sed -i 's/echo -n "3.9.2"/echo -n "3.9.3"/' scripts/remove-ads.sh
   ```

3. **Коммит и push:**

   ```bash
   git add -A
   git commit --no-verify -m "chore: bump version to 3.9.3"
   git push origin main
   ```

4. **Создайте тег:**

   ```bash
   git tag v3.9.3
   git push origin v3.9.3
   ```

5. **GitHub Actions** запускает `Build and Release` — собирает релиз.

**Что вы видите:**

- Новый тег `v3.9.3`.
- Через 10–15 минут — релиз `v3.9.3` с архивом.
- Обновляете панель через `install.sh` или кнопку «Обновить».

> **Правило:** версия в файле `internal/config/version` **должна совпадать** с тегом. Тогда кнопка «Обновить» **неактивна** после обновления.

#### Сценарий 3: Обычный день (ничего не происходит)

**Что происходит автоматически:**

1. **03:00 UTC** — `Sync Upstream` запускается.
2. Проверяет upstream.
3. Ничего нового у Санаи — `Already up to date`.
4. Завершается.

**Что вы видите:**

- **Ничего.** Workflow зелёный, но без изменений.
- **Всё работает** как есть.

### Зачем такая схема

**Плюсы:**

- ✅ `Sync Upstream` — **автоматически** подтягивает код Санаи. Вам **не нужно** следить за обновлениями.

- ✅ **Вы контролируете**, когда выходит новая версия.
- ✅ **Никаких сюрпризов** — релиз только по вашей команде.

**Минусы:**

- ⚠️ **Ручная работа** — раз в неделю-месяц надо создать тег.
- ⚠️ **Не автоматически** — надо зайти в SSH или GitHub.

### Что попадает в релиз, а что нет

**Важно понимать разницу** между **синхронизацией кода** и **релизом**.

| Что | Когда попадает в `main` | Когда попадает в релиз |
|---|---|---|
| **Коммиты Санаи** (багфиксы, улучшения) | ✅ Автоматически (`Sync Upstream`) | ⏳ Только при **создании нового тега** |
| **Удаление рекламы** (`remove-ads.sh`) | ✅ Автоматически | ✅ Всегда (при сборке) |
| **jsDelivr-замены** | ✅ Автоматически | ✅ Всегда (при сборке) |
| **Брендирование** (`panel.go`, `update.sh`) | ✅ Автоматически | ✅ Всегда (при сборке) |

**Что это значит на практике:**

1. **`Sync Upstream`** раз в день подтягивает **новые коммиты** Санаи в `main`. **Это не релиз** — это **обновление кода**.
2. **Релиз** создаётся **только** когда **вы создаёте тег** `v*`. В этот момент GitHub Actions **собирает бинарник** из **текущего `main`**.
3. **Некритические фиксы** (например, багфиксы Санаи **без** нового релиза) — **не попадают** в релиз, пока вы **не создадите новый тег**.

**Пример:**

- Санаи **запушил 3 багфикса** в `main` (WireGuard, renewal, TUIC) — **но не выпустил релиз**.
- Ваш `Sync Upstream` **подтянул** эти багфиксы в `main`.
- **В `main`** — багфиксы **есть**.
- **В релизе `v3.9.2`** — багфиксов **нет** (потому что релиз **собран раньше**).
- Чтобы багфиксы **попали в релиз** — надо **создать новый тег** (`v3.9.3` или **пересобрать `v3.9.2`**).

**Когда стоит выпускать новый релиз:**

- ✅ Санаи выпустил **новый стабильный релиз** (например, `v3.10.0`).
- ✅ Накопились **важные багфиксы**, которые нужны **в бинарнике**.
- ✅ Вы **сами** внесли **значимые изменения**.
- ❌ **Не стоит** выпускать новый релиз **на каждый коммит** Санаи — это **засорит** историю релизов.

**Правило:** версия в файле `internal/config/version` **должна совпадать** с тегом. Тогда кнопка «Обновить» **неактивна** после обновления.
